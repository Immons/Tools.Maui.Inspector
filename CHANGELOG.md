# Changelog

## 0.10.5

- Fix: the visual-root scan (0.10.3) could crash the app. After a window-hosted popup closed, its root still pointed at a platform view whose native peer was already disposed, and the scan's 1.5 s timer read `IsAttachedToWindow` (Android) / `Window` (iOS) on it — `ObjectDisposedException` on the main loop. A disposed view now counts as off screen, and the scan logs a warning instead of throwing.

## 0.10.4

- Inspector tab: the element tree lists the visual roots outside the page tree that the memory tracker learned to see in 0.10.3 — overlays hosted on the platform window (`… · window overlay`) and roots reported through `Memory.TrackVisualRoot` or as an `Element` to `Navigation.ReportPushed` (`… · reported root`) — as top-level nodes after the window's page, with the modals, in the platform's stacking order (topmost last: the `UIWindow`'s subview order on iOS, the decor view's child order on Android, where a modal's dialog window is above every overlay of the activity). Their children are walked like any element's, so select mode, Mirror tap-to-select, highlight bounds, the property panel, the XAML view, `/api/find`, `/api/tap` and the console dump reach them; an overlay covering the page is hit before the page. A Crate.Maui `CrateResponsivePopup` (root with the window as its `Parent`, view on the `UIWindow` / decor view) is the case this was built for.
- The roots come from the same registry as the memory tracker: the element tree re-scans the platform window whenever it is read (with tracking off too), the web panel's 1 s poll carries a `tseq` that changes when an overlay opens or closes and reloads the tree then, and the on-device panel and highlight layers are put back above an overlay added after them. A selection inside an overlay that closes is dropped.
- Sample: *Modal page* (with its own window-overlay button) and the `HV_WINDOW_OVERLAY=n` test hook.

## 0.10.3

- Memory: overlays hosted outside the window's page tree are tracked. A popup library that portals into the window — the root gets the MAUI `Window` as its `Parent` (or none) and its platform view is added straight to the `UIWindow` (iOS) or the activity's decor view (Android) — raises no `DescendantAdded` on the window, so none of its elements ever appeared in the snapshot rows and a leak in it was only visible in a heap dump. The tracker now scans the platform window's direct children every 1.5 s and before every snapshot, maps the MAUI views among them back to their elements (`MauiView.View` / `CrossPlatformLayout`, through `WrapperView`) and tracks their trees with the same hints and holders as a page's; the root's own descendant events keep the tree current while it is up. `options.Memory.DiscoverVisualRoots` (default on) switches the scan off.
- Memory: "attached" means "under a live root". An element whose top ancestor has the window as `Parent` but is not its page, a modal or another visual child of the window is attached only while its platform view is in a platform window (`UIView.Window` / `View.IsAttachedToWindow`), so an overlay taken off the screen with its `Parent` still pointing at the window shows as detached instead of attached forever. Page trees are judged as before; where the platform cannot tell (Windows, plain `net10.0`) the old answer stands.
- New `Immons.Tools.Maui.Inspector.Memory.TrackVisualRoot(Element)` / `UntrackVisualRoot(Element)` for roots kept anywhere else (a native container of the app's own): the tree is tracked and counts as attached until untracked. An `Element` passed to `Navigation.ReportPushed` is a visual root as well until `ReportPopped`. Weak references only — a root never untracked is not kept alive by the inspector.
- Sample: *Window overlay*, *Leaky window overlay* and *Reported* buttons — an overlay on the platform window (clean; leaky with `Parent` left on the window; reported through `Memory.TrackVisualRoot` from a native container of the page).

## 0.10.2

- Web server: a client that goes away — a closed panel tab, a phone or Mac that slept, a dropped Wi-Fi, `maui-inspector-sync` polls queued while the app was suspended — no longer surfaces in the app as `TaskScheduler.UnobservedTaskException` ("Broken pipe", "ObjectDisposed … HttpListenerResponse"), which crash reporters record as unhandled errors of the app. The cause sat inside `System.Net.HttpListener`'s managed implementation (iOS, Android, every Unix): its writes go through `BeginWrite`/`EndWrite`, and when the socket is closed under a pending write — most often by the listener rebuild on returning to the foreground — `EndWrite` throws before it reaches `Socket.EndSend`, and its own error page (`HttpConnection.SendError`) throws from a thread-pool callback; neither task is ever observed, and neither path can be reached from outside `HttpListener`. The inspector now serves HTTP/1.1 itself on a plain socket (keep-alive, `Content-Length` and chunked request bodies, `Expect: 100-continue`, HEAD, bounded heads/bodies and send timeouts): every socket operation is awaited by the code that started it, a dropped client ends its exchange quietly (a line in the debugger output only — not in the Logs view), and real server failures are still logged as warnings. Endpoints and routes are unchanged; `HttpResponse.Write*` report a dropped client as `false` instead of throwing.
- Every fire-and-forget task of the inspector (request dispatch, listener restarts and watchdog, network-change debounce, watch-mode snapshots, Cookbook open/close/focus, Properties scroll, the ping's window-size read left behind on a busy main thread) is now observed: a failure is logged and never reaches `TaskScheduler.UnobservedTaskException`.
- New `tests/HttpServerTests`: real loopback sockets — requests, keep-alive, chunked and 100-continue bodies, a 32 MB response; resets in the middle of a large response, of a long poll and of a stream of writes; 200 aborted exchanges of every shape; shutdown with writes in flight; the supervisor rebuilding the real listener; then `GC.Collect` + `WaitForPendingFinalizers` and no unobserved task exception. An informational baseline runs the same storm against `HttpListener` (16 unobserved exceptions from 216 exchanges on macOS). The sample prints anything that reaches `UnobservedTaskException`/`UnhandledException`.

## 0.10.1

- MAUI 11: the Cookbook's visual-state chips work again. `VisualStateManager.GetVisualStateGroups` returns `VisualStateGroupList` in MAUI 11 instead of `IList<VisualStateGroup>`, so the call compiled against MAUI 10 was a missing method there — `MissingMethodException` on CoreCLR/Mono, "will always throw" from ILC under NativeAOT. The groups are now read through `VisualStateManager.VisualStateGroupsProperty`, which has the same shape in both. New `tests/MauiCompatTests` checks the names on MAUI 10 and 11 and that the call does not come back.
- Android: `Debug.getMemoryInfo` (PSS and graphics memory of the Memory view) no longer runs on the UI thread. It was read inside snapshot classification and the navigation ledger, both of which run on the main thread, and with large mappings or right after the snapshot's collections it can take hundreds of milliseconds — an ANR dump caught the UI thread inside it. Reads are still at most one per 5 s and one at a time; from the main thread they go to the thread pool (the caller gets the previous reading), elsewhere they run in place. Snapshots take their memory reading before hopping to the main thread. The read is a named trace section (`MauiInspector.getMemoryInfo`) in systrace/Perfetto.

## 0.10.0

- SignalR view: new package `Immons.Tools.Maui.Inspector.SignalR` with one line on the `HubConnectionBuilder` — `.WithMauiInspector("chat")`, in any position of the chain, inert unless `UseMauiInspector` was called. The web panel's new 📡 SignalR tab shows each hub's state (Connecting / Connected / Reconnecting / Disconnected) with transport, protocol, connection id, traffic counters, last ping, last error and a reconnect counter, plus a timeline of messages in both directions (invocations, stream items, completions with invoke → completion time, pings, close, retries and failed attempts) with filters by hub and text, pause, clear and formatted details. Arguments are masked (token, password, authorization, bearer strings, JWTs…) and capped at 4 KB before they are stored; a ring buffer keeps 1000 events per hub. Works with JSON, Newtonsoft and MessagePack; the bytes on the wire are never changed.
- SignalR: 💉 Inject — a developer tool that delivers a server → client call to the app's `On(...)` handler as if the server had sent it (text protocols, not with stateful reconnect; `AllowInjection = false` turns it off).
- HTTP API: `GET /api/signalr`, `GET /api/signalr/events?hub=&since=&method=&limit=`, `GET /api/signalr/event?seq=`, `POST /api/signalr/pause`, `/clear`, `/inject`.
- Sample: a SignalR demo page and a small SignalR server (`samples/Immons.Tools.Maui.Inspector.SignalRServer`); the iOS sample uses the UIKit scene lifecycle required by the iOS 27 SDK.
- Web panel smoke tests: `CDP_PORT` / `CDP_USER_DATA_DIR` let `cdp.mjs` drive an installed Chrome; `signalr.smoke.mjs` walks the SignalR view.
- Web server: survives the app going to the background. iOS reclaims a suspended app's listening sockets — afterwards the port still completed TCP handshakes (`nc -z` said open) but HttpListener's internal accept never fired again, so every HTTP request timed out until the app was restarted. The listening socket is now rebuilt on the same port when the app returns to the foreground (iOS: always; Android: when a loopback self-probe gets no answer) and when the network comes back or switches interfaces, with retries while the port is still held (auto-assigned servers move to another free port of the range as a last resort). A watchdog probes `/api/ping?probe=1` through loopback every 15 s while the app is in the foreground and rebuilds the socket after two misses in a row. The accept loop no longer dies silently on an exception: it logs, backs off and rebuilds the socket after repeated failures. `/api/ping` reports `listenerRestarts`.
- maui-inspector-sync: finds physical phones and tablets on the Wi-Fi. Next to localhost it sweeps the /24 subnet of the Mac's Wi-Fi/Ethernet on ports 9295–9299 (parallel TCP connects, ~2 s, repeated every minute; VPN, AirDrop, VM bridges, cellular and non-private ranges excluded; `--no-lan-scan` / `MAUI_INSPECTOR_NO_LAN_SCAN=1` to switch off). New `--host <ip|name|ip:port>` / `--url <url>` (repeatable, comma-separated; a bare host tries 9295–9309) and the `MAUI_INSPECTOR_HOSTS` variable name devices explicitly. New `maui-inspector-sync discover` lists every inspector found (with the other URLs of the same app) without watching. Localhost probing is now parallel. No Bonjour/UDP: it would need `NSBonjourServices` + the Local Network prompt in every app, or Apple's multicast entitlement.
- Web panel: the header device picker gains *Scan local network…* (the page's own app sweeps its subnet through the new `GET /api/discover`) and *Add address…*; found devices are remembered and also offered by the Devices tab (*📶 Scan network*). The same app reachable on localhost and a LAN address is listed once.
- Device labels: `/api/ping` has a new `label` with the model for physical devices (`KidsTime · iPhone (iPhone18,2) · iOS 27.2 · Device`), used by the picker, the Devices tab and the sync tool; the tree header shows the model too. The ping's `device` string is unchanged (panels key per-device browser storage on it).
- Network tab: a call is listed the moment it is sent — a pending row (⏳) with method, URL without its query, start time, live duration and, for uploads, bytes sent vs. `Content-Length` (`120.0 MB / 300.0 MB ↑`); downloads count received bytes while the app reads them. Opened row details survive the live updates.
- Network capture no longer buffers large bodies. Before, a body without a Content-Type (or a textual one) was loaded into memory with `LoadIntoBufferAsync` before its size was checked — a 300 MB upload sat in memory before the first byte left. Now the decision is made from the headers: textual bodies known to fit under `MaxCapturedBodyBytes` are buffered, textual bodies of unknown length are copied while the transport reads them (tee, capped), untyped bodies count as binary and known-large ones are not read; the same for responses (large downloads). Bodies are wrapped so both handler styles keep streaming (`CopyToAsync` — SocketsHttpHandler/Android, `ReadAsStreamAsync` — NSUrlSessionHandler). A breakpoint on a body of unknown length reads at most the cap ahead. The scenario recorder gets streamed response bodies when the app has read them.
